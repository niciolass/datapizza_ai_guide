STAGE 02 Tools & @tool decorator stage2_tools.py
Creating a tool
from datapizza.tools import tool

@tool
def get_time(timezone: str) -> str:
    """Returns current time in timezone."""
    from datetime import datetime
    import zoneinfo
    tz = zoneinfo.ZoneInfo(timezone)
    return datetime.now(tz).strftime("%H:%M %Z")

# @tool reads: name, docstring, type annotations
# → auto-generates JSON schema for the LLM
get_time.name    # "get_time"
get_time.schema  # generated JSON schema
tool_choice options
ValueBehaviour
"auto"Model decides whether to call a tool
"required"Must call at least one tool
"required_first"Calls a tool first, then reasons
"none"No tools, answer from knowledge only
["tool_name"]Forces that specific tool
response = client.invoke(
  "question",
  tools=[get_time, calculator],
  tool_choice="auto",
)
How tools work underground
1. LLM receives tools as JSON schema in request → Returns ToolUseBlock (name + args), not output 2. Framework finds Python fn by name, calls it → Appends result as "tool" role message 3. Full history re-sent to LLM → LLM writes final answer using result

Agent vs client.invoke()
Agent handles automatically:
memory No manual add_turn() needed — agent updates memory after each step
tool loop Runs tool → appends result → re-invokes LLM until done
planning When planning_interval > 0, writes a plan before acting
reset agent.memory.reset() — clears without re-instantiating
Session persistence pattern
# Serialize
def memory_to_dict(memory) -> list[dict]:
    return [
      {"role": t.role.value,
       "text": t.content.text}
      for t in memory.turns
    ]

# Restore
def dict_to_memory(turns) -> Memory:
    memory = Memory()
    for t in turns:
        memory.add_turn(
          TextBlock(content=t["text"]),
          role=ROLE(t["role"]))
    return memory

# Inject at construction
agent = Agent(..., memory=dict_to_memory(db_turns))
FastAPI session pattern
# In-memory LRU cache (single server)
_cache: dict[str, Agent] = {}

def get_agent(session_id):
    if session_id not in _cache:
        stored = load_from_db(session_id)
        _cache[session_id] = Agent(
          ...,
          memory=dict_to_memory(stored)
        )
    return _cache[session_id]

@app.post("/chat")
async def chat(session_id, message):
    agent = get_agent(session_id)
    r = await agent.a_run(message)
    save_to_db(session_id, agent.memory)
    return {"reply": r.text}

Wiring agents together

manager = Agent(
  name="manager",
  client=client,
  planning_interval=1,  # critical for multi-agent
  max_steps=6,
)

# Registers specialists as callable tools
manager.can_call([researcher, writer])

# Inspect what manager can call
[t.name for t in manager.tools]
# → ["researcher", "writer"]

Key concepts
can_call() Registers sub-agent as a @tool on the manager — works exactly like a regular tool under the hood
isolation Each agent has its own isolated Memory. Specialist memory resets per invocation — only manager is stateful
planning planning_interval=1 makes manager write a plan before delegating — dramatically improves reliability
pattern Manager = orchestrator/stateful. Specialists = stateless workers focused on one task

dag = DagPipeline(

Quick reference — Key concepts

response.content blocks

Every response contains typed blocks: TextBlock (final text), ToolUseBlock (LLM requested a tool call with name + args), ToolResultBlock (the function's return value). Filter by type to inspect what happened.

Tool execution loop

The LLM never executes code — it returns a structured ToolUseBlock. The framework finds your Python function by name, calls it, appends the result as a "tool" role message, and re-sends everything to the LLM. This loop repeats until the LLM returns a TextBlock with no tool calls.

Agent memory isolation

In a multi-agent system, each agent owns its own Memory. Sub-agents are stateless workers — their memory resets per invocation from the manager. Only the manager maintains a growing stateful conversation history.

planning_interval

When set > 0, the agent writes an explicit plan (a TextBlock listing intended steps) before taking any action. This commits the model to a strategy rather than improvising, dramatically improving reliability on multi-step and multi-agent tasks.

DagPipeline Connection

source_key: which key in the source node's return dict to extract. target_key: which parameter name of the destination node's _run() to pass it to. Two connections from the same source node = two separate values being passed downstream.

Tracing spans

One span = one LLM call. In a multi-agent trace, you'll see one span per agent invocation. Per-span token counts reveal cost distribution: the manager is typically cheap (few tokens), specialists are where tokens accumulate.
